# 模块 01：前端交互层 / Agent Console MVP 能力说明（修订版）

## 1. 当前模块

当前讨论模块：

```text
模块 01：前端交互层 / Agent Console
```

该模块是用户与可控工程 Agent 的统一交互入口。

在 MVP 中，用户不需要先选择具体业务 Agent。用户面对的是一个“总体 Agent / 工程智能助手 / 主控 Agent”，由系统根据用户输入、当前工程上下文、当前软件模块和可用 Agent 配置，自动判断本次任务应该调用哪个具体业务 Agent。

同时，MVP 版本需要加入前后端体系：

```text
前端负责：输入、展示、选择、确认、预览、审批、查看结果；
后端负责：配置读取、模型/API 校验、Agent 路由、工作流控制、工具调用、日志追踪；
模型网关负责：真正对接大模型 API，统一调用、重试、降级和统计。
```

因此，前端可以提供“大模型和 API 通道选择入口”，但不能直接调用大模型 API，也不能直接保存敏感 API Key。

---

## 2. MVP 总体框架流程

MVP 整体运行链路调整为：

```text
用户输入自然语言
↓
前端总入口接收任务
↓
用户可选择模型 / API 通道，或使用系统默认配置
↓
前端提交用户输入、当前项目、当前对象、模型选择信息
↓
后端加载总体 Agent 配置
↓
后端校验模型 / API 是否可用、是否授权
↓
加载当前工程上下文
↓
IntentRouter 识别用户意图
↓
AgentRouter 判断应调用哪个业务 Agent
↓
前端显示本次调用的业务 Agent
↓
后端加载业务 Agent 配置
↓
绑定模型策略、Schema、Prompt、Skill、规则、工具和审批策略
↓
LLM 提取结构化参数
↓
Schema 校验参数
↓
规则层补默认值、推导、校验
↓
生成工具调用计划
↓
执行 DryRun 预演
↓
前端展示预览结果、影响范围、风险提示
↓
用户确认 / 修改 / 取消
↓
后端正式执行
↓
前端展示执行结果
↓
Trace 记录全过程
```

前端模块主要覆盖其中这些节点：

```text
统一任务入口
↓
总体 Agent 状态展示
↓
模型 / API 选择入口
↓
业务 Agent 路由结果展示
↓
参数展示
↓
规则结果展示
↓
DryRun 预览展示
↓
用户审批
↓
执行结果展示
↓
Trace 查看入口
```

## 3. 模块定位

前端交互层的定位是：

```text
让用户通过一个统一入口提出工程任务，并清楚看到系统理解、路由、参数、规则、预演、确认和执行全过程。
```

前端同时提供有限的运行配置入口，例如：

```text
选择大模型；
选择 API 通道；
查看当前模型配置；
查看当前业务 Agent；
查看当前任务状态；
查看 DryRun 预览；
确认是否执行。
```

但前端不直接做业务判断，也不直接修改工程数据。

前端的核心职责是：

```text
1. 提供统一 Agent 入口；
2. 接收用户自然语言输入；
3. 展示总体 Agent 状态；
4. 提供模型 / API 选择入口；
5. 展示系统自动路由到的业务 Agent；
6. 展示结构化参数；
7. 展示默认值和参数来源；
8. 展示规则命中结果；
9. 展示 DryRun 影响范围；
10. 让用户确认、取消或修改；
11. 展示执行结果；
12. 提供 Trace 查看入口。
```

前端不是：

```text
1. 业务 Agent 路由器；
2. 规则引擎；
3. 工具调用器；
4. 工程数据修改器；
5. 模型 API 直接调用器；
6. API Key 存储器；
7. 绕过审批的执行入口。
```

## 4. MVP 中必须实现的前端能力

### 4.1 Agent 状态展示

前端展示的 Agent 状态需要分成两层：

```text
第一层：总体 Agent 状态；
第二层：本次任务调用的业务 Agent 状态。
```

#### 4.1.1 总体 Agent

总体 Agent 是用户看到的统一入口。

示例：

```text
总体 Agent：EICAD 工程智能助手
```

它的作用是：

```text
接收所有自然语言任务；
读取当前工程上下文；
根据用户输入判断任务类型；
调用 IntentRouter 和 AgentRouter；
把任务分发给具体业务 Agent；
统一展示执行状态、结果和日志。
```

总体 Agent 不直接完成所有业务逻辑，而是负责统一入口和任务分发。

#### 4.1.2 本次调用的业务 Agent

业务 Agent 是系统自动判断后调用的具体能力模块。

示例：

```text
本次调用 Agent：路基模板创建 Agent
```

其他后续可能出现的业务 Agent 包括：

```text
横断面戴帽 Agent；
超高加宽 Agent；
结构层统计 Agent；
纵断面检查 Agent；
平纵指标审核 Agent；
软件功能问答 Agent；
专业知识问答 Agent；
出表算量 Agent。
```

业务 Agent 不需要用户手动选择，而是由系统根据意图识别和上下文自动判断。

前端需要展示该判断结果，例如：

```text
系统判断：当前任务属于“路基模板创建”
本次调用：路基模板创建 Agent
置信度：高
可切换：否 / 可人工调整
```

#### 4.1.3 前端状态栏建议展示内容

前端顶部状态栏不应只显示一个“当前 Agent”，而应显示：

```text
总体 Agent；
本次调用 Agent；
当前项目；
当前软件模块；
当前选中对象；
当前任务状态；
当前模型；
当前 API 通道；
当前规则版本；
当前工具权限范围。
```

MVP 中可以简化为：

```text
总体 Agent：EICAD 工程智能助手
本次调用：路基模板创建 Agent
模型：GPT / DeepSeek / 通义 / 私有化模型等
API 通道：公司默认 / 用户自定义 / 内网私有化
项目：当前打开工程
对象：当前路线 / 当前断面 / 当前模板
状态：等待输入 / 路由判断中 / 参数提取中 / 待确认 / 执行中 / 已完成 / 失败
```

状态流转建议为：

```text
等待输入
↓
任务识别中
↓
业务 Agent 判断中
↓
业务 Agent 已确定
↓
参数提取中
↓
规则校验中
↓
DryRun 预演中
↓
等待用户确认
↓
执行中
↓
已完成 / 失败 / 已取消
```

### 4.2 模型 / API 选择入口

MVP 前端需要提供模型和 API 通道选择能力。

用户可以选择：

```text
使用系统默认模型；
选择指定模型；
选择指定 API 通道；
查看当前模型能力说明；
查看当前模型是否支持结构化输出；
查看当前模型是否支持工具调用；
查看当前模型是否可用于当前 Agent。
```

示例展示：

```text
模型：GPT-4.1 / DeepSeek-V3 / 通义千问 / 本地私有化模型
API 通道：公司默认 API / 项目专用 API / 用户自定义 API / 内网模型服务
```

注意：

```text
前端只提交用户选择的 model_id、provider_id、api_channel_id；
前端不直接调用模型 API；
前端不保存明文 API Key；
后端负责校验模型和 API 是否可用；
模型网关负责实际调用。
```

如果允许用户录入 API Key，建议处理方式是：

```text
前端只提供录入入口；
提交给后端后由后端加密保存或临时使用；
前端不回显完整 Key；
Trace 中不记录明文 Key；
调用时由 Model Gateway 使用 credential_ref 获取。
```

MVP 中推荐优先支持：

```text
系统预置 API 通道；
用户在前端选择模型；
用户在前端选择 API 通道；
后端配置中心校验权限；
模型网关实际调用。
```

暂不建议一开始开放复杂的用户自定义 Key 管理。

---

### 4.3 自然语言输入区

用户可以直接输入自然语言任务，例如：

```text
帮我创建一个高速公路路基模板，设计速度 80，路基宽度 24.5 米。
```

用户不需要先选择“路基模板创建 Agent”。

输入区需要支持：

```text
自然语言输入；
多轮补充；
任务取消；
重新生成；
清空当前任务。
```

MVP 中不需要复杂多模态输入，也不需要语音输入。

---

### 4.4 业务 Agent 路由结果展示

系统识别任务后，前端应展示业务 Agent 路由结果。

展示内容：

```text
识别出的用户意图；
匹配到的业务 Agent；
匹配原因；
置信度；
是否需要用户确认；
是否允许用户手动切换。
```

示例：

```text
识别意图：创建路基模板
匹配业务 Agent：路基模板创建 Agent
匹配原因：用户输入中包含“创建”“高速公路”“路基模板”等任务信息
置信度：0.91
处理方式：自动进入参数提取
```

如果系统不确定，则进入澄清：

```text
系统判断该任务可能属于以下能力：
1. 路基模板创建 Agent
2. 横断面戴帽 Agent
3. 软件功能问答 Agent

请确认你想执行的是哪一类任务。
```

MVP 中可以先支持：

```text
高置信度：自动进入业务 Agent；
低置信度：让用户确认业务方向；
无法判断：作为问答任务处理或提示用户补充。
```

---

### 4.5 参数提取结果展示

LLM 提取参数后，前端必须以结构化表单展示，而不是只显示一段文字。

参数面板至少展示：

```text
字段名称；
字段值；
单位；
来源；
是否必填；
是否可修改；
校验状态；
说明。
```

字段来源需要明确标记：

```text
用户输入；
模型提取；
系统上下文；
项目配置；
规则默认；
规则推导；
用户确认。
```

示例：

```text
道路等级：高速公路｜来源：用户输入｜状态：通过
设计速度：80 km/h｜来源：用户输入｜状态：通过
路基宽度：24.5 m｜来源：用户输入｜状态：通过
边坡形式：默认边坡｜来源：规则默认｜状态：待确认
```

---

### 4.6 缺失参数与追问展示

如果参数不足，前端不应直接执行，而应进入追问状态。

前端展示方式：

```text
缺少关键参数；
缺少原因；
是否必须填写；
可选默认值；
用户补充入口。
```

示例：

```text
缺少：边坡类型
原因：创建路基模板需要明确边坡策略
处理方式：可选择项目默认边坡，或手动指定
```

用户可以选择：

```text
采用默认值；
手动填写；
取消任务；
查看更多说明。
```

### 4.7 规则命中结果展示

规则层执行后，前端必须展示规则命中结果。

展示内容：

```text
命中的规则；
规则类型；
规则结果；
参数变更；
是否阻断；
是否需要确认；
解释说明。
```

规则结果分级：

```text
阻断错误；
警告；
提示；
自动修复；
需要确认。
```

---

### 4.8 DryRun 预览展示

DryRun 是 MVP 前端最核心的界面之一。

前端必须展示：

```text
将要执行什么动作；
影响哪些工程对象；
使用哪些参数；
哪些参数来自用户；
哪些参数来自规则；
哪些对象会被新增；
哪些对象会被修改；
是否会保存；
是否支持回滚；
风险等级；
警告信息。
```

DryRun 结果可以用“动作清单”展示：

```text
动作 1：读取当前路线信息
动作 2：生成路基模板草稿
动作 3：预览模板对当前断面的影响
动作 4：等待用户确认后应用模板
```

如果当前任务会修改工程对象，必须明确提示：

```text
该操作将修改当前工程对象，执行前需要用户确认。
```

---

### 4.9 用户审批区

用户审批不是简单的“确定 / 取消”，而是确认一份动作说明。

MVP 至少支持：

```text
确认执行；
取消任务；
修改参数；
查看规则说明；
查看影响范围。
```

审批按钮建议：

```text
确认执行
修改参数
取消任务
查看详情
```

---

### 4.10 执行结果展示

正式执行完成后，前端需要展示：

```text
执行是否成功；
实际执行了哪些动作；
生成或修改了哪些对象；
是否保存；
是否可回滚；
警告信息；
错误信息；
下一步建议。
```

失败时需要展示：

```text
失败节点；
失败原因；
错误码；
用户可采取的处理方式；
是否已回滚。
```

### 4.11 Trace 查看入口

MVP 不需要复杂日志平台，但前端必须提供 Trace 入口。

用户或研发人员至少可以查看：

```text
run_id；
用户原始输入；
总体 Agent；
业务 Agent；
模型配置；
API 通道；
模型输出；
参数提取结果；
规则命中结果；
DryRun 结果；
用户确认记录；
工具调用结果；
执行结果；
错误信息。
```

注意：

```text
Trace 不得记录明文 API Key；
只记录 model_id、provider_id、api_channel_id、credential_ref 或脱敏信息。
```

## 5. 前端最小页面结构

MVP 建议前端包含 9 个区域：

```text
1. 顶部状态栏
2. 模型 / API 选择区
3. 对话输入区
4. 业务 Agent 路由结果区
5. 参数确认面板
6. 规则结果面板
7. DryRun 预览面板
8. 用户审批区
9. 执行结果与 Trace 区
```

页面结构示意：

```text
┌────────────────────────────────────────────┐
│ 顶部状态栏：总体 Agent / 项目 / 对象 / 状态   │
├────────────────────────────────────────────┤

├────────────────────────────────────────────┤

├────────────────────────────────────────────┤
│ 路由区：本次调用 Agent / 意图 / 置信度         │
├────────────────────────────────────────────┤
│ 参数面板：字段 / 值 / 来源 / 状态             │
├────────────────────────────────────────────┤
│ 规则面板：规则命中 / 警告 / 阻断              │
├────────────────────────────────────────────┤
```

## 6. 前端输入输出契约

### 6.1 前端输入给后端

前端向后端提交时，不应强依赖具体业务 Agent，而是提交总体 Agent 上下文、用户输入和模型选择信息。

```json
{
  "user_input": "",
  "main_agent_id": "engineering_assistant",
  "project_id": "",
  "module_id": "",
  "selected_object_ids": [],
  "session_id": "",
  "model_selection": {
    "model_id": "",
    "provider_id": "",
    "api_channel_id": "",
    "use_default": true
  },
  "user_action": "submit"
}
```

其中：

```text
main_agent_id：总体 Agent，例如 EICAD 工程智能助手；
user_input：用户自然语言输入；
project_id：当前工程；
module_id：当前软件模块；
selected_object_ids：当前选中对象；
session_id：当前会话；
model_selection：用户选择的大模型和 API 通道。
```

不建议前端一开始就传：

```json
{
  "current_agent_id": "subgrade_template_agent"
}
```

因为具体业务 Agent 应由后端判断，而不是由用户或前端提前指定。

---

### 6.2 后端返回给前端

后端返回时，需要明确告诉前端：

```text
总体 Agent 是谁；
识别出的意图是什么；
本次调用了哪个业务 Agent；
为什么调用它；
当前使用哪个模型；
当前使用哪个 API 通道；
当前工作流状态是什么。
```

返回结构建议：

```json
{
  "run_id": "",
  "main_agent": {
    "agent_id": "engineering_assistant",
    "agent_name": "EICAD 工程智能助手"
  },
  "routed_agent": {
    "agent_id": "subgrade_template_agent",
    "agent_name": "路基模板创建 Agent",
    "confidence": 0.91,
    "route_reason": "用户输入包含创建路基模板任务，并提供了道路等级、设计速度、路基宽度等参数。"
  },
  "model_runtime": {
    "model_id": "",
    "provider_id": "",
    "api_channel_id": "",
    "model_status": "available"
  },
  "workflow_state": "",
  "intent": "",
  "params": [],
  "rule_hits": [],
  "validation_results": [],
  "dry_run_result": {},
  "approval_required": true,
  "messages": [],
  "errors": []
}
```

---

### 6.3 用户审批输入

用户审批时，前端提交：

```json
{
  "run_id": "",
  "approval_action": "approve",
  "modified_params": {},
  "comment": ""
}
```

审批基于 run_id，而不是重新指定业务 Agent 或模型 API。

## 7. 与其他模块的关系

前端交互层依赖以下模块：

```text
总体 Agent 配置：展示统一入口；
Agent 配置中心：获取 Agent 和模型配置；
Model Config 后端服务：提供可选模型和 API 通道；
IntentRouter：识别用户意图；
AgentRouter：判断本次调用哪个业务 Agent；
上下文管理层：获取当前项目、对象、状态；
模型网关：间接触发模型调用；
Schema 校验层：展示参数合法性；
规则引擎：展示默认值、推导和校验结果；
Tool Registry：展示可执行动作；
DryRun Executor：展示预演结果；
Approval Gate：执行用户确认；
Trace Logger：查看运行日志。
```

前端不能直接依赖：

```text
LLM API；
CAD / BIM 内部函数；
工程数据写入接口；
未注册工具；
未授权规则；
具体业务 Agent 的内部实现；
明文 API Key。
```

---

## 8. MVP 不做范围

前端 MVP 暂不做：

```text
复杂后台管理；
多 Agent 可视化编排；
完整权限管理后台；
复杂日志检索平台；
模型效果对比平台；
多客户配置管理；
灰度发布管理；
大型知识库管理；
复杂 BI 报表；
语音输入；
多模态图纸识别。
```

但需要预留入口：

```text
模型配置入口；
API 通道配置入口；
总体 Agent 配置入口；
业务 Agent 路由说明入口；
Trace 调试入口；
规则说明入口；
知识来源入口；
权限提示入口。
```

---

## 9. MVP 验收标准

前端模块完成后，应满足以下标准：

```text
1. 用户能通过统一入口输入自然语言任务；
2. 用户不需要手动选择具体业务 Agent；
3. 系统能展示总体 Agent；
4. 系统能展示本次自动调用的业务 Agent；
5. 用户能看到为什么调用该业务 Agent；
6. 低置信度时，系统能让用户确认业务方向；
7. 用户能看到当前项目和当前对象；
8. 用户能选择大模型；
9. 用户能选择 API 通道；
10. 前端不会直接调用模型 API；
11. 前端不会保存或回显明文 API Key；
12. 用户能看到模型提取出的结构化参数；
13. 用户能区分参数来源；
14. 用户能看到缺失参数和追问；
15. 用户能看到规则命中结果；
16. 用户能看到 DryRun 影响范围；
17. 用户能在执行前确认或取消；
18. 用户能修改参数后重新计算；
19. 用户能看到执行结果；
20. 用户能看到错误原因；
21. 用户能查看或复制 Trace ID；
22. 前端不能绕过后端工作流直接执行工具；
23. 前端不能直接修改工程数据。
```

---

## 10. 本模块结论

前端交互层的 MVP 核心不是让用户选择一个具体 Agent 来执行任务，而是提供一个统一的工程智能助手入口。

正确的设计应是：

```text
用户面对总体 Agent；
用户可以选择模型和 API 通道；
后端校验模型/API 配置；
系统自动判断业务 Agent；
前端展示判断结果；
用户确认关键动作；
后端受控执行工具。
```

因此，前端中“Agent 状态展示”应改为：

```text
总体 Agent 状态 + 本次调用业务 Agent 状态 + 当前模型/API 状态
```

而不是单独显示：

```text
当前 Agent：路基模板创建 Agent
```

推荐命名：

```text
总体 Agent：EICAD 工程智能助手
本次调用 Agent：路基模板创建 Agent
当前模型：用户选择或系统默认模型
当前 API：用户选择或系统默认 API 通道
```

这样既符合用户自然使用习惯，也符合后续多 Agent 和多模型扩展方向。
